MLOps project · Python · interview guide

Sentiment analysis, from notebook to a monitored service on Kubernetes

An end-to-end MLOps project: experiments tracked in MLflow on DagsHub, a 6-stage DVC pipeline, a model registry with Staging and Production, tests as a quality gate, GitHub Actions CI/CD, a Docker image on AWS ECR, two pods on AWS EKS, and Prometheus + Grafana monitoring. This guide starts from zero (TF-IDF, logistic regression, metrics, uncertainty) and walks through every file, every pipeline stage, every CI step and every Kubernetes line, with the results, the bugs, the weak spots and the questions you'll be asked.

0. Your pitch

30 seconds

"I built an end-to-end sentiment analysis system on IMDB reviews. I compared Bag-of-Words and TF-IDF across five algorithms and tuned logistic regression, which took F1 from 0.71 to 0.82 and recall from 66% to 83%. But the main focus was taking the model beyond the notebook: a reproducible DVC pipeline, experiment tracking and a model registry in MLflow, automated tests and deployment with GitHub Actions, and a Docker container on AWS Kubernetes with Prometheus and Grafana monitoring."

The 2-minute version

  1. Problem. Companies get thousands of reviews; reading them by hand is slow. Most models die inside a notebook, so I built the whole journey to a live, monitored service.
  2. Data. 500 labelled IMDB reviews, balanced: 249 positive, 251 negative.
  3. Cleaning. Remove URLs and numbers, lowercase, strip punctuation and stop words, lemmatize.
  4. Modelling. Baseline BoW + logistic regression: 70.4% accuracy. Then 10 runs (BoW vs TF-IDF × 5 algorithms): TF-IDF + logistic regression won. GridSearchCV (5-fold, optimising F1): C = 10, L2 → 80% accuracy, 83% recall, F1 0.82.
  5. Engineering. The notebook became a 6-stage DVC pipeline. Every run is logged to MLflow on DagsHub and the model is registered. On every push GitHub Actions reruns the pipeline, tests the model, promotes it to Production, tests the app, builds a Docker image, pushes it to ECR and deploys it to EKS (2 replicas behind a LoadBalancer).
  6. Monitoring. The app exposes request count, latency and per-class prediction counts; Prometheus scrapes them and Grafana charts them.
  7. Challenge. 22 CI runs to get green. Hardest: DagsHub's login opened a browser, and a CI runner has none, so it hung. I switched to token auth from GitHub Secrets.
  8. Learning. The model is maybe 20% of the work. Reproducibility, testing, deployment and monitoring are the other 80%.
Say this honestly if pushed

The 80% / 0.82 numbers come from the tuning experiment (80/20 split). The production DVC pipeline uses different settings (75/25 split, only 50 TF-IDF features) and logs its own metrics, which you should look up on DagsHub before the interview (§15).

1. What MLOps is, and why a model needs it

Analogy

A notebook is a recipe a chef cooked once at home. A restaurant needs the recipe written down exactly, the same ingredients every time, a taste test before serving, a kitchen that serves many customers, and someone checking whether customers are happy. This project builds that restaurant around the model.

"Which experiment was best? I forgot."MLflow on DagsHubRemembers every run: settings, scores, the model file

"What if a server dies or traffic grows?"Kubernetes, 2 replicasRestarts crashed pods, spreads traffic
"Is the live app healthy?"Prometheus + GrafanaCounts requests, measures latency, live charts

MLOps maturity levels (Google's framing)

  • Level 0, manual: notebooks, hand-copied models.
  • Level 1, pipeline automation: a reproducible training pipeline, tracking, a registry, continuous training (CT) when data changes.
  • Level 2, CI/CD for pipelines: the pipeline itself is tested and deployed automatically.

This project sits around level 1 with CI/CD: the pipeline retrains and redeploys on every code push. What's missing for full level 2: retraining triggered by new data or drift, and a real promotion gate (§29).

Why ML is harder than normal software: behaviour depends on code and data and model, any of which can change; a model can be "wrong" without crashing; and the world it predicts drifts away from the training data.

2. Splits, cross-validation and data leakage

  • Train / test split: the test set is the final exam the model never saw. Scoring on training data is grading a student on questions they memorised.
  • random_state=42 fixes the shuffle, so every run gets the same split and experiments are comparable.
  • Stratified split keeps the class ratio equal in both parts (stratify=y). Not used here; with 249/251 it barely matters, but it's free.
  • k-fold cross-validation: split the training data into k parts, train on k−1, test on the remaining one, rotate k times, average. Gives a more stable estimate than one split and is what GridSearchCV(cv=5) does for every hyper-parameter combination.
  • Data leakage: information from the test set influencing training, so scores look better than reality. Classic case: fitting a scaler or vectorizer on all the data before splitting. The vectorizer's vocabulary and IDF weights then "know" the test reviews.
Where leakage happens in this project (and where it doesn't)

The DVC pipeline is clean: feature_engineering.py calls fit_transform on train and only transform on test. The experiments are not: exp1.ipynb (CountVectorizer), exp2_bow_vs_tfidf.py:113-115 and exp3_lor_tf_idf_hp.py:63-67 all fit the vectorizer on all 500 reviews, then split. With TF-IDF the effect is mild (vocabulary and IDF only, no labels), but it makes the experiment scores slightly optimistic. Saying this yourself is a strong signal (§15).

  • Lemmatization vs stemming: stemming chops endings by rule ("studies" → "studi"); lemmatization uses a dictionary ("studies" → "study"). Slower, real words. Note WordNet's lemmatizer treats every word as a noun by default, so "running" stays "running".
  • The negation trap: NLTK's English stop-word list contains not, no, nor (and "don't", "isn't"…). "not good" becomes "good": the sentiment flips. Keep negations, or use bigrams so "not_good" is its own feature.

4. Bag-of-Words and TF-IDF, with the actual formula

Bag of Words: count each word; ignore order. "good good movie" → good = 2, movie = 1.

TF-IDF = how often the word is in this review × how rare it is across all reviews. scikit-learn's default (smooth_idf=True):

tf(t, d)  = count of term t in document d
idf(t)    = ln( (1 + n) / (1 + df(t)) ) + 1     # n = number of documents, df = documents containing t
tfidf     = tf × idf, then each row is L2-normalised (length 1)

Worked example, 4 reviews (n = 4): "movie" appears in all 4, "masterpiece" in 1.

  • idf(movie) = ln(5/5) + 1 = 1.00
  • idf(masterpiece) = ln(5/2) + 1 ≈ 1.92
  • So in "movie masterpiece", masterpiece gets almost twice the weight. Common words are pushed down, distinctive words up. After L2 normalisation, long and short reviews are comparable.
  • max_features=N keeps the N most frequent terms (by count across the training set). The pipeline uses 50 (params.yaml); the experiments used the full vocabulary. 50 is very small: many sentiment words are simply dropped.
  • The result is a sparse matrix (mostly zeros). The pipeline converts it to dense with .toarray() to write CSVs: fine at 50 columns, wasteful at 50,000.
  • n-grams: ngram_range=(1,2) adds word pairs ("not good", "well done") and helps sentiment a lot.
  • Embeddings / BERT: dense vectors that capture meaning and context (sarcasm, negation). More accurate with enough data, but heavier to serve and less explainable. With 500 rows and a focus on MLOps, TF-IDF + a linear model is the right call.

5. Logistic regression, with the maths

  1. Each feature (word) j has a weight wj; plus a bias b. Positive words get positive weights.
  2. Score: z = w · x + b (sum of weight × TF-IDF value).
  3. Probability: p = σ(z) = 1 / (1 + e−z), squashed into (0, 1).
  4. Prediction: positive if p ≥ 0.5, i.e. z ≥ 0.
  5. Training minimises log loss (cross-entropy): −[y log p + (1−y) log(1−p)], averaged over reviews, plus a regularisation penalty. Convex, so there's one global optimum.

Why "regression"? It's a linear regression on the log-odds: log(p / (1−p)) = w · x + b. A weight of 0.7 on "wonderful" means each unit of that feature multiplies the odds of "positive" by e0.7 ≈ 2.

Why it suits text: sparse, high-dimensional features where classes are roughly linearly separable; fast; tiny to serve; gives probabilities; you can read the top positive and negative words off the weights.

6. Regularisation, C, L1 vs L2, solvers

  • Regularisation penalises large weights so the model doesn't memorise the training data (overfitting).
  • scikit-learn minimises roughly C × Σ log-loss + ½‖w‖² (L2) or C × Σ log-loss + ‖w‖₁ (L1). So C is the inverse of the penalty strength: small C = strong penalty, cautious model; big C = weak penalty, trusts the data.
  • Your grid: C ∈ {0.1, 1, 10} × {L1, L2}. At C = 0.1 the penalty was so strong the model predicted almost everything negative (recall 0.33; 0.00 with L1). C = 10, L2 won.
  • L1 (lasso) pushes some weights to exactly zero: built-in feature selection. L2 (ridge) shrinks all weights smoothly. With few features and little data, L2 kept more useful signal.
  • Solver: the optimisation algorithm. liblinear (coordinate descent) is good for small datasets and supports both L1 and L2; lbfgs (the default) supports only L2; saga scales to large sparse data and supports both.
  • Bias–variance: strong regularisation → high bias (underfits); weak → high variance (overfits). CV picks the middle.

7. Metrics, worked on your confusion matrix

The tuned model on the 100-review experiment test set (54 truly positive, 46 negative):

  • Why harmonic mean? It punishes imbalance: precision 0.94 with recall 0.54 gives F1 ≈ 0.68 (your Naive Bayes case). You can't hide a weak metric behind a strong one.
  • ROC curve: true-positive rate vs false-positive rate at every threshold. AUC = probability a random positive is ranked above a random negative; 0.5 random, 1.0 perfect. The pipeline logs it.
  • PR curve / PR-AUC: precision vs recall over thresholds; more informative than ROC when positives are rare.
  • Threshold: 0.5 is a default, not a law. Use predict_proba and pick the threshold from the PR curve to match the business cost (raise for precision, lower for recall).
  • Precision or recall? Precision when false alarms are expensive (auto-publishing "positive testimonials"); recall when misses are expensive (catching every angry customer).

8. How sure are we? Small test sets and fair comparisons

An interviewer with a statistics background will ask this. Be ready.

  • Confidence interval for accuracy: with n = 100, 80% has a standard error of √(0.8 × 0.2 / 100) = 0.04, so a 95% interval of about 0.80 ± 0.078 → [72%, 88%]. The baseline's 70.4% is just outside, but…
  • …the baseline (exp1) and the champion (exp3) were measured on different splits (75/25 vs 80/20) with different vectorizers. A fair comparison scores both models on the same test rows and uses a paired test like McNemar (only the reviews where they disagree matter).
  • CV F1 0.726 ± 0.038 vs test F1 0.818: the cross-validated number averages 5 splits and is the more honest estimate. The single test split was a bit easy. Quote both, trust CV.
  • Variance from small data: with 500 reviews, which rows land in the test set moves scores by several points. More data, repeated CV, or bootstrap intervals would make the conclusions firmer.
Say it like this

"The improvement is consistent in direction across CV and the test split, but with 100 test reviews the interval is about ±8 points, so I'd treat the exact gap as approximate. To claim it rigorously I'd score both models on the same split, run McNemar, and use the full 50,000-review IMDB set."

Part 3

The experiments

Baseline, comparison, tuning: evidence before code.

12. Experiment 1: the baseline

  • notebooks/exp1.ipynb: CountVectorizer(max_features=150) (Bag of Words, top 150 words) + default LogisticRegression, 75/25 split, random_state=42, logged to MLflow ("Logistic Regression Baseline").
  • Result: accuracy 70.4%, precision 78.0%, recall 65.7%, F1 0.713.
  • Reading it: precise but misses a third of positive reviews. Raw counts let frequent, uninformative words dominate.
  • Why a baseline first? Without it, "80%" means nothing. Random guessing on balanced data gives ~50%; the baseline sets the bar a real model must beat.

13. Experiment 2: BoW vs TF-IDF × 5 algorithms

  • exp2_bow_vs_tfidf.py: one parent MLflow run ("All Experiments") with 10 nested child runs, one per {vectorizer × algorithm}, 80/20 split, default hyper-parameters, full vocabulary.
  • Algorithms: Logistic Regression, Multinomial Naive Bayes, XGBoost, Random Forest, Gradient Boosting.
  • Each child logs vectorizer, algorithm, test_size, model params, accuracy/precision/recall/F1, and the model.
FindingNumbersWhy
TF-IDF + LogReg wonaccuracy 0.79, F1 0.807 (BoW + LogReg F1 0.789)TF-IDF down-weights common words; linear models benefit from its scaling
Naive Bayes + TF-IDF: a trapprecision 0.935, recall 0.537, F1 0.682Only says "positive" when very sure, so it misses half: one great metric can hide a bad model
XGBoost worstaccuracy 0.63–0.68Many parameters, 400 training rows: overfits; boosting needs more data

A detail worth knowing

The script reuses the same estimator object across the two vectorizers (model = algorithm), so each fit overwrites the previous one. That's fine because every run refits from scratch, but cloning (sklearn.base.clone) would be cleaner.

14. Experiment 3: tuning with GridSearchCV

  • exp3_lor_tf_idf_hp.py: TF-IDF (full vocabulary), 80/20 split, GridSearchCV(LogisticRegression(), param_grid, cv=5, scoring="f1", n_jobs=-1).
  • Grid: C ∈ {0.1, 1, 10}, penalty ∈ {l1, l2}, solver liblinear → 6 combinations × 5 folds = 30 fits (+1 refit on all training data).
  • Each combination is logged as a child run with its mean CV F1; the best params, best CV F1 and the model are logged on the parent.
  • Winner: C = 10, L2. Test: accuracy 0.80, precision 0.804, recall 0.833, F1 0.818; CV F1 0.726 ± 0.038.
  • Why optimise F1? It balances precision and recall, so the search can't "win" by being over-cautious like Naive Bayes.
  • Overall vs baseline: +9.6 points accuracy, +17.6 recall, +10.5 F1. Across the four MLflow experiment groups (baseline, comparison, tuning, pipeline): 36+ runs.

15. Reading the experiments honestly

  1. CV vs test. CV F1 0.726 is the more stable estimate; test F1 0.818 came from one lucky-ish split of 100 reviews (§8).
  2. Leakage in the experiments. All three fit the vectorizer on all 500 reviews before splitting (§2). Mild for TF-IDF, but the scores are slightly optimistic. The DVC pipeline fixed it.
  3. Experiments ≠ production config. The pipeline uses 75/25 and max_features=50; the tuned experiment used 80/20 and the full vocabulary. C=10 is hard-coded in model_building.py, not in params.yaml. So the deployed model's metrics are whatever the "my-dvc-pipeline" MLflow experiment shows, not necessarily 80%. Check DagsHub before the interview.
  4. Different splits. Baseline (75/25, BoW-150) and champion (80/20, TF-IDF) weren't scored on the same rows, so the gap is approximate (§8).
Say it like this

"I chose TF-IDF + logistic regression from tracked evidence: a baseline, a controlled 10-run comparison, then cross-validated tuning. Looking back, the experiments fitted the vectorizer before splitting, which inflates scores slightly, and the pipeline uses fewer features than the tuned config. My production pipeline fixes the leakage, and I'd move every hyper-parameter into params.yaml so the pipeline mirrors the champion exactly."

Part 4

The DVC pipeline, stage by stage

From a CSV on the internet to a registered model.

16. DVC from zero

  • Problem: Git is great for code, bad for large data and model files.
  • DVC stores data and models in a content-addressed cache (files named by their MD5 hash) and keeps small pointer files / lock entries in Git. Big files go to a remote (here s3://capstone-data-12) with dvc push/dvc pull.
  • dvc.yaml declares stages: a command, its deps (code and data it reads), params (keys from params.yaml), outs (files it produces) and metrics. Together they form a DAG (directed acyclic graph).
  • dvc.lock records the hash of every dep, param and out from the last successful run: the exact recipe that produced the model.
  • dvc repro walks the DAG and reruns only stages whose deps or params changed (like make). Change max_features → only feature engineering and everything after it rerun.
  • dvc status shows what's out of date; dvc dag prints the graph; dvc metrics show prints metrics.json.

Two subtleties
  • model_evaluation doesn't list data/processed as a dep, yet it reads test_tfidf.csv. Usually harmless (a new test set also changes model.pkl), but deps should list everything a stage reads.
  • Hyper-parameters aren't params: C=10 is in code, so changing it reruns training only because the script changed, and dvc.lock doesn't show the value.

18. Stage 1, data_ingestion.py

  1. load_params('params.yaml') → test_size = 0.25.
  2. load_data(url): reads a 500-row CSV straight from a public GitHub URL. (The S3 path via s3_connection.py is written but commented out.)
  3. preprocess_data: keep rows whose sentiment is positive or negative; map positive → 1, negative → 0.
  4. train_test_split(test_size=0.25, random_state=42) → 375 train / 125 test (not stratified).
  5. Write data/raw/train.csv and test.csv.

Every function logs and re-raises; main() catches everything, logs and prints the error (§24 explains why that's a problem).

Reproducibility gap: the source is a URL DVC doesn't track. If its content changed, the pipeline wouldn't know. Fix: dvc import-url or version the raw CSV in the S3 remote.

19. Stage 2, data_preprocessing.py

preprocess_text applies, in this order: remove URLs → remove digits → lowercase → punctuation to spaces (also an Arabic semicolon), squeeze whitespace → drop NLTK English stop words → WordNet lemmatize. Applied to the review column of train and test separately, then written to data/interim/.

  • nltk.download('wordnet') and ('stopwords') run at import: needs network on first run.
  • The "remove sentences under 3 words" step is commented out; dropna afterwards does nothing in practice.
  • Applying the cleaning to train and test separately is fine: it's a fixed function, nothing is "fitted".

20. Stage 3, feature_engineering.py

  1. Read params → max_features = 50.
  2. Load the interim CSVs; fillna('') so empty reviews don't crash the vectorizer.
  3. TfidfVectorizer(max_features=50): fit_transform on train, transform on test. No leakage.
  4. Convert to dense DataFrames (50 columns named 0..49) and append a label column.
  5. Pickle the vectorizer to models/vectorizer.pkl: the live app must use exactly this vocabulary and these IDF weights.
  6. Write data/processed/train_tfidf.csv and test_tfidf.csv.

21. Stage 4, model_building.py

Read train_tfidf.csv, X = all columns but the last, y = the last; LogisticRegression(C=10, solver='liblinear', penalty='l2').fit(X, y); pickle to models/model.pkl. Training takes milliseconds.

Pickle, briefly

Pickle serialises Python objects. It's convenient but tied to library versions (a model pickled with one scikit-learn version may not load in another) and unsafe to load from untrusted sources (unpickling can run code). MLflow's model format adds the environment (conda/requirements) and a signature on top.

22. Stage 5, model_evaluation.py

  1. At import: read the DagsHub token from CAPSTONE_TEST (or dagshub_token), put it in MLFLOW_TRACKING_USERNAME and PASSWORD, and set the tracking URI to https://dagshub.com/satyagudu1146/MLOPS-PROJ-CI-CD.mlflow. No browser login (the CI fix, §36).
  2. mlflow.set_experiment("my-dvc-pipeline"), start a run.
  3. Load model.pkl and test_tfidf.csv; predict labels and probabilities.
  4. Compute accuracy, precision, recall, ROC-AUC (not F1); write reports/metrics.json.
  5. Log the metrics, every model parameter (get_params()), the model (mlflow.sklearn.log_model(clf, "model")) and metrics.json as an artifact.
  6. Write reports/experiment_info.json = {run_id, model_path: "model"}: the hand-off to registration.

23. Stage 6, register_model.py

  1. Same token-based MLflow setup.
  2. Read experiment_info.json → model URI runs:/<run_id>/model.
  3. mlflow.register_model(uri, "my_model") creates a new version (1, 2, 3…).
  4. client.transition_model_version_stage(name, version, "Staging").

So every pipeline run registers a new version in Staging. Promotion to Production happens later, in CI, after the tests pass (§26).

24. Logging and error handling (and a silent-failure trap)

  • src/logger/__init__.py configures the root logger once at import: a RotatingFileHandler (5 MB, 3 backups, one timestamped file per process in logs/) and a console handler, both at INFO.
  • Every helper logs and re-raises (good).
  • But every main() wraps everything in try/except Exception, logs and prints the error, and returns normally. The process exits with code 0.
Why that matters

DVC and GitHub Actions decide success by the exit code. If ingestion fails (URL down), the stage "succeeds", DVC moves on, and the failure only shows up later as a confusing error in a downstream stage, or as stale outputs being reused. Fix: re-raise (or sys.exit(1)) in main() so the pipeline fails fast at the real cause.

Part 5

MLflow: tracking and the registry

The memory of the project.

25. Experiment tracking

  • Experiment = a named group of runs ("Bow vs TfIdf", "LoR Hyperparameter Tuning", "my-dvc-pipeline"…). Run = one execution, with params (inputs), metrics (numbers, can be logged per step), artifacts (files: the model, metrics.json, plots) and tags (git commit, user).
  • Nested runs: a parent run with children, used for the 10-way comparison and the grid search, so they stay grouped in the UI.
  • DagsHub hosts an MLflow tracking server per repo, so runs are shared and survive your laptop; authentication is HTTP basic auth, where both username and password can be the access token.
  • Why not a spreadsheet? MLflow logs automatically, links metrics to the exact params and model file, compares runs side by side, and turns a run into a deployable versioned model.
  • MLflow model format: log_model saves the model plus an MLmodel file describing "flavours" (sklearn, and the generic pyfunc with a predict(DataFrame) interface) and the Python environment. The app and tests load it as mlflow.pyfunc.load_model(...), which is why they pass a DataFrame with string column names.

26. The Model Registry and promotion

  • A registered model ("my_model") has numbered versions, each pointing to a run's model artifact.
  • Each version has a stage: None → Staging (being tested) → Production (live) → Archived (retired).
  • scripts/promote_model.py: take the newest Staging version; move every current Production version to Archived; move the new one to Production. Rollback = move an older version back to Production and restart the pods.
  • Consumers ask for a model by name and stage/version (models:/my_model/Production) instead of a file path, so deployment and model updates are decoupled.
Two things to know
  • Stages are deprecated since MLflow 2.9 in favour of aliases (e.g. @champion, @challenger) and tags. transition_model_version_stage and get_latest_versions still work in 2.19 but warn. Mention you'd migrate.
  • The app loads Staging, not Production: get_latest_model_version in app.py asks for the newest Staging version (else unstaged). The README says Production. Since CI promotes right after testing, they're usually the same version, but the clean design is to load models:/my_model@champion explicitly.

Testing: the quality gate

What's checked before a model reaches users, and what should be.

27. tests/test_model.py

setUpClass (runs once): token auth, find the newest Staging version of my_model, load it as pyfunc, load vectorizer.pkl, load the holdout data/processed/test_tfidf.csv.

TestWhat it checksWhat it catches
test_model_loaded_properlyThe model object isn't NoneRegistry or auth problems, missing artifacts
test_model_signatureVectorise "hi how are you" → DataFrame with as many columns as the vectorizer's vocabulary; the model returns one prediction per row, as a 1-D arrayA model trained with a different vectorizer / feature count; wrong output shape

The weak threshold

0.40 is below random guessing (0.50) on balanced data, so nearly any model passes. It's a smoke test, not a quality gate. Better: thresholds near the known baseline (~0.70), and a champion vs challenger check: promote only if the new model beats the current Production model on the same holdout set.

28. tests/test_flask_app.py

  • Uses Flask's app.test_client(): requests are handled in-process, no server needed.
  • test_home_page: GET / → 200 and the page title is "Sentiment Analysis".
  • test_predict_page: POST /predict with "I love this!" → 200 and the page contains "Positive" or "Negative".
  • Side effect: from flask_app.app import app runs app.py's top-level code, which authenticates and downloads the model from MLflow. That's why these tests need the token and must run after a model exists (CI story 3, §36).
  • The template renders "😊 Positive Sentiment" or "😞 Negative Sentiment", so the check proves a prediction happened, not that it's right. A stricter test would assert the label for a few unambiguous reviews.

29. What a production-grade gate would add

  • Data tests: schema (columns, types), no empty reviews, label balance within bounds, no train/test overlap (e.g. Great Expectations / pandera).
  • Behavioural tests (CheckList style): invariance ("I loved the movie" vs "I loved the film" → same label), directional ("good" → "not good" should lower the score), minimum-functionality cases.
  • Champion vs challenger on a fixed holdout, with a minimum improvement and a significance test.
  • Latency and size budgets: model loads under N seconds, predicts under M ms.
  • Training–serving parity test: the app's cleaning and the pipeline's cleaning give identical output on sample texts (it would catch §31).
Part 7

Serving: Flask, Gunicorn and Docker

How a model becomes an HTTP service in a container.

30. flask_app/app.py, top to bottom

  1. Cleaning helpers (lines 18-68): the same six operations as training, wrapped in normalize_text.
  2. Auth at import (73-85): token from CAPSTONE_TEST → MLflow env vars → tracking URI on DagsHub. Missing token → the app refuses to start (EnvironmentError).
  3. Prometheus registry (101-112): a custom CollectorRegistry with three metrics: app_request_count (Counter, labels method and endpoint), app_request_latency_seconds (Histogram, label endpoint), model_prediction_count (Counter, label prediction). A custom registry means /metrics shows only these, not Python process metrics.
  4. Model loading at import (116-128): find the newest Staging version of my_model (else the newest unstaged), load it with mlflow.pyfunc.load_model("models:/my_model/<v>"); load models/vectorizer.pkl from the image. This happens once per worker process, at start-up.
  5. GET /: count, render the form, observe latency.
  6. POST /predict: count → normalize_text → vectorizer.transform → dense DataFrame with columns "0"…"49" (the pyfunc model expects the same column names it was logged with) → model.predict → count the predicted class → observe latency → render.
  7. GET /metrics: generate_latest(registry) in the Prometheus text format.
  8. app.run(debug=True, host="0.0.0.0", port=5000) only when run directly; in the container gunicorn imports app:app instead. (Debug mode must never be used in production: it exposes an interactive debugger.)
Small code smells to know
  • remove_small_sentences uses np, which isn't imported. It's never called, so it never fails.
  • Stop words are rebuilt as a set and a lemmatizer is created on every request: cheap here, but should be created once at start-up.
  • No input validation: an empty or huge text is processed as-is.

31. Training–serving skew: the cleaning order differs

StepTraining (data_preprocessing.py)Serving (app.py)
1Remove URLsLowercase
2Remove digitsRemove stop words
3LowercaseRemove digits
4Punctuation → spacesPunctuation → spaces
5Remove stop wordsRemove URLs (too late)
6LemmatizeLemmatize

Concrete failure: "great https://imdb.com" → training removes the URL first → "great". Serving replaces punctuation first, so the URL becomes "https imdb com", no longer matches the URL regex, and survives as three words. Also, serving removes stop words before punctuation, so in "it was so, so good" the token "so," (with its comma) isn't in the stop list, and after punctuation is stripped it survives as "so". Training would have removed it. The model then sees tokens it never saw in training.

With max_features=50 most such tokens fall outside the vocabulary and are ignored, so the damage is small, but it's exactly the class of bug that silently degrades models in production.

The fix to describe

One shared cleaning function imported by both, or better, a single scikit-learn Pipeline (FunctionTransformer(clean) → TfidfVectorizer → LogisticRegression) logged to MLflow as one model. Then the app sends raw text and can never drift from training. Plus a parity test in CI (§29).

32. Gunicorn and workers

  • Flask's built-in server is for development: one process, not hardened. Gunicorn is a production WSGI server: a master process managing worker processes, restarting dead workers and enforcing timeouts.
  • The image runs gunicorn --bind 0.0.0.0:5000 --timeout 120 app:app. With no --workers, gunicorn starts 1 sync worker: one request at a time per pod. A common setting is (2 × cores) + 1.
  • --timeout 120: a worker silent for 120 s is killed and restarted. Raised because loading the model from DagsHub at start-up can be slow.
  • Prometheus with several workers: each worker process has its own counters, so a scrape hits one worker and sees only its numbers. With more than one worker you need the client's multiprocess mode (a shared directory via PROMETHEUS_MULTIPROC_DIR). With one worker the problem doesn't arise.
  • Gunicorn isn't in flask_app/requirements.txt; it (and scikit-learn, needed to unpickle the model) arrive as dependencies of the full mlflow package. Works, but list them explicitly.

33. The Dockerfile, line by line

FROM python:3.10-slim                         # small Debian image with Python 3.10
WORKDIR /app
COPY flask_app/ /app/                         # app.py, templates/, requirements.txt
COPY models/vectorizer.pkl /app/models/vectorizer.pkl   # same vectorizer as training
RUN pip install -r requirements.txt
RUN python -m nltk.downloader stopwords wordnet          # NLTK data baked in
EXPOSE 5000
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "--timeout", "120", "app:app"]
  • Images are layers: each instruction creates a cached layer; a rebuild reuses layers until the first changed instruction.
  • Caching improvement: copy only requirements.txt first, pip install, then copy the app. Today any change to app.py invalidates the pip layer and reinstalls everything.
  • pip install --no-cache-dir keeps the image smaller.
  • Security: runs as root (add a non-root USER); no secrets inside: the DagsHub token is injected at runtime as an environment variable from a Kubernetes Secret.
  • The model isn't in the image: it's downloaded from DagsHub when the pod starts (§44 discusses the trade-off).
  • Multi-stage builds and a .dockerignore help larger projects; a HEALTHCHECK is handled by Kubernetes probes instead.

Reconciliation loop: you declare the desired state (2 pods); controllers continuously compare it with the actual state and fix differences. Kill a pod and a new one appears.

38. deployment.yaml, line by line

kind: Deployment            name: flask-app
replicas: 2                                     # two copies for availability
selector.matchLabels: app=flask-app             # which pods belong to it
template.metadata.labels: app=flask-app         # label stamped on each pod

  requests: memory 256Mi, cpu 250m             # reserved for scheduling

---
kind: Service  type: LoadBalancer  selector app=flask-app  port 5000 → targetPort 5000
  • Requests vs limits: the scheduler places a pod only on a node with the requested resources free. Above the CPU limit the container is throttled; above the memory limit it's OOM-killed and restarted. 250m = a quarter of a CPU core.
  • With requests below limits the pod is in the Burstable QoS class (Guaranteed if equal; BestEffort if none).
  • imagePullPolicy defaults to Always for :latest, so a restarted pod pulls the newest image; but nothing restarts them on deploy (§34).
  • What's missing: readiness and liveness probes, a rolling-update strategy tuned to the slow start-up, an HPA, a namespace, and a pinned image tag.

39. Probes, rollouts, rollback, scaling

  • Readiness probe: "can this pod take traffic?" (e.g. HTTP GET / returns 200). Until it passes, the Service doesn't send requests. Important here because a pod spends its first seconds downloading the model.
  • Liveness probe: "is it stuck?" If it fails repeatedly, Kubernetes restarts the container.
  • Startup probe: a longer grace period for slow-starting apps before liveness kicks in.
  • Rolling update (the Deployment default): replace pods gradually (maxSurge, maxUnavailable), so there's no downtime if readiness probes exist.
  • Rollback: kubectl rollout undo deployment/flask-app returns to the previous ReplicaSet, which only helps if images have distinct tags. For the model, move the previous registry version back to Production and restart pods.
  • Horizontal Pod Autoscaler: scale replicas on CPU or custom metrics (e.g. requests per second from Prometheus). Needs CPU requests set (they are) and metrics-server.
  • Useful commands: kubectl get pods -o wide, kubectl describe pod <p>, kubectl logs <p>, kubectl get svc (the external LB hostname), kubectl rollout status deployment/flask-app.

40. AWS pieces and cost

  • ECR: a private Docker registry; CI pushes the image, EKS nodes pull it (their IAM role needs ECR read permission).
  • EKS: managed Kubernetes control plane (charged per hour, about $0.10/h) plus the EC2 worker nodes and the ELB, all charged while running, even idle.
  • S3: the DVC remote (s3://capstone-data-12).
  • IAM: who may do what. CI uses an access key; nodes use an instance role; better practice is OIDC roles for CI and IRSA (IAM roles for service accounts) for pods.
  • Cost control: you deleted the cluster, node group and ECR images right after validating and taking screenshots. For this traffic, one container on App Runner / ECS Fargate / a small VM would be enough. EKS was chosen to learn production-grade orchestration; say so.
Part 10

Monitoring

System health today, model health next.

41. Prometheus from zero

  • Pull model: Prometheus scrapes each target's /metrics every few seconds (scrape interval, often 15 s) and stores time series (metric name + labels → timestamped values).
  • Metric types: Counter only goes up (requests, predictions); Gauge goes up and down (in-flight requests, memory); Histogram counts observations into buckets (latency), so percentiles can be computed; Summary computes quantiles in the client (can't be aggregated across pods).
  • Why a histogram for latency: averages hide slow requests; p95/p99 show what the slowest users experience. The default buckets go from 5 ms to 10 s.
  • PromQL you can quote: 
    rate(app_request_count_total{endpoint="/predict"}[5m])            # requests per second
histogram_quantile(0.95, sum by (le) (rate(app_request_latency_seconds_bucket[5m])))   # p95 latency
sum by (prediction) (rate(model_prediction_count_total[1h]))     # predictions per class
  • The Python client adds _total to counter names in the exposition format; histograms expose _bucket, _sum, _count.
  • Scraping pods correctly: each pod keeps its own counters. If Prometheus scrapes through the LoadBalancer address, each scrape lands on a random pod and the series jumps between two counters. The right way is per-pod discovery (Kubernetes service discovery, or a ServiceMonitor with the Prometheus Operator) and sum() in queries.

42. Grafana and alerting

  • Grafana queries Prometheus and draws panels: request rate per endpoint, p95 latency, predictions per class over time (screenshots are in the repo's EKS RUNS_img/).
  • The four golden signals (Google SRE): latency, traffic, errors, saturation. You have the first two; errors (count 5xx responses) and saturation (CPU/memory per pod) are the next panels to add.
  • Alerts (Alertmanager or Grafana alerting): p95 latency above a threshold for 5 minutes, error rate above 1%, prediction mix drifting (§43).

43. Model monitoring: drift and real accuracy

  • Data drift: the inputs change (new slang, a new product, longer reviews). Concept drift: the input→label relationship changes (a word's meaning shifts). Both silently degrade a once-good model.
  • What you already have: model_prediction_count by class, a crude drift signal: if the app suddenly predicts 90% negative, something changed.
  • Population Stability Index: bin a feature (or the predicted probability) in training vs live data; PSI = Σ (live% − train%) × ln(live% / train%). Rule of thumb: < 0.1 stable, 0.1–0.25 moderate shift, > 0.25 significant.
  • Kolmogorov–Smirnov test: largest gap between two cumulative distributions (e.g. review length), with a p-value.
  • Vocabulary coverage: the share of incoming words that are in the vectorizer's vocabulary; a drop means the language moved.
  • Real accuracy needs labels: collect user feedback or label a small random sample weekly, compute metrics, and trigger retraining through the same DVC pipeline when performance drops (continuous training).
  • Tools: Evidently AI, WhyLabs, or custom Prometheus metrics.

45. If you rebuilt it for production

  1. One model artifact: sklearn Pipeline (clean → TF-IDF with bigrams and negations → LogReg), with a signature and input example, logged to MLflow.

  8. Model upgrade with more data: DistilBERT fine-tuned, served with ONNX Runtime or a dedicated model server; compare cost/latency against TF-IDF before switching.

Full 50k IMDB, bigrams and negation-aware cleaning, one sklearn Pipeline artifact to remove skew, a champion-vs-challenger gate, git-SHA image tags with rollout restarts, probes, drift monitoring, and a DistilBERT comparison.

Data and features
Is 500 reviews enough?easy

Enough to prove the pipeline, small for NLP. Scores move with the split (CV F1 ±0.038; ±8 points on a 100-review test). I'd scale to 50k.

Why check class balance?easy

With 90% positives, "always positive" scores 90% accuracy. Mine is 249/251, so accuracy is meaningful, but I still report precision, recall and F1.

What if the data were imbalanced?medium

Stratified splits, per-class recall, F1 and PR-AUC instead of accuracy, class_weight='balanced', or resampling, and threshold tuning.

Explain TF-IDF and its formula.medium

Term count in the review × idf = ln((1+n)/(1+df)) + 1, then each row L2-normalised. Words in every review get idf 1; rare ones get more weight.

Why did TF-IDF beat BoW for logistic regression?medium

Raw counts let common words dominate; TF-IDF down-weights them and normalises length, highlighting discriminative words. F1 0.789 → 0.807.

What does max_features do, and is 50 a good value?medium

Keeps the N most frequent terms. 50 is very small: it controls noise and size but drops many sentiment words. The tuned experiment used the full vocabulary; I'd tune it as a parameter.

Is removing stop words always good for sentiment?hard

No. NLTK's list includes not/no/nor, so "not good" becomes "good". Keep negations or use bigrams.

What is data leakage? Did you have any?hard

Test information influencing training. The pipeline fits TF-IDF on train only. The experiments fitted the vectorizer on all 500 reviews before splitting, a mild leak (vocabulary and IDF), so those scores are slightly optimistic.

Why save vectorizer.pkl separately?medium

The model only understands the exact columns that fitted vectorizer produces. Serving must use the same vocabulary and IDF weights, otherwise columns mean different words.

Why not word embeddings or BERT?medium

500 rows, a focus on MLOps, and serving cost. TF-IDF + LogReg is tiny, fast on CPU and explainable. With more data a fine-tuned DistilBERT would likely win on context and sarcasm.

Model and evaluation
Explain logistic regression to a non-technical person.easy

Every word has a positive or negative score; add up the scores of the review's words and turn the total into a probability. Above 50%, positive.

Why is it called regression?medium

It's a linear regression on the log-odds, log(p/(1−p)) = w·x + b; a threshold turns the probability into a class.

What loss does it minimise?hard

Log loss (binary cross-entropy) plus a regularisation term. It's convex, so the optimum is global.

What is C? L1 vs L2?medium

C is the inverse regularisation strength: small = strong penalty. L1 zeroes some weights (feature selection); L2 shrinks all smoothly. C=10, L2 won; C=0.1 predicted almost everything negative.

What is GridSearchCV doing exactly?medium

For each of 6 combinations, 5-fold CV on the training data (30 fits), scored by F1; picks the best mean, then refits it on all training data.

Precision and recall with your numbers.easy

Of 56 predicted positive, 45 were right: precision 0.80. Of 54 truly positive, 45 found: recall 0.83.

Why the harmonic mean for F1?medium

It punishes imbalance: precision 0.94 with recall 0.54 gives F1 ≈ 0.68, so one strong metric can't hide a weak one.

What is ROC-AUC?medium

The probability a random positive is ranked above a random negative; the area under TPR vs FPR across thresholds. 0.5 random, 1 perfect. The pipeline logs it.

Test F1 0.818 but CV F1 0.726. Which do you trust?hard

CV: it averages 5 splits. One 100-review split happened to be easy. I report both and trust CV.

Is 80% vs 70.4% a real improvement?hard

Probably, but not proven by these numbers: ±8 points at n=100, different splits and vectorizers, and mild leakage. I'd score both on the same rows and use McNemar.

How would you change the 0.5 threshold?medium

Use predict_proba and the precision-recall curve; pick the threshold that matches the cost of false positives vs false negatives.

Why did XGBoost do worst?medium

Powerful models with many parameters overfit 400 training rows; linear models usually win on small, sparse text.

Pipeline, tracking, registry
What is DVC, and how is it different from Git?easy

Git versions code; DVC versions data, models and pipelines, storing big files in a content-addressed cache and a remote (S3) with small pointers in Git. dvc.yaml defines stages; dvc.lock stores hashes.

Change max_features and run dvc repro: what happens?medium

Ingestion and preprocessing are skipped; feature engineering and every stage after it rerun.

Your stages catch all exceptions. Problem?hard

Yes: they print and exit 0, so DVC and CI think they succeeded and the error surfaces later, somewhere confusing. main() should re-raise.

How do you make an experiment reproducible?medium

Fixed seeds, pinned versions, parameters in config, versioned data, every run logged, everything run from scripts not notebook cells.

Why MLflow instead of a spreadsheet?easy

It logs params, metrics, code version and the model file together, compares runs, and turns the best run into a versioned deployable model.

What does the registry give you? How do you roll back?medium

Versions with stages. Consumers ask for "Production" instead of a file. Rollback: move the previous version back to Production and restart the pods.

MLflow stages are deprecated. What replaces them?hard

Aliases (e.g. @champion, @challenger) and tags. I'd load models:/my_model@champion and move the alias on promotion.

Which model does your app actually load?hard

The newest Staging version (README says Production). CI promotes right after testing, so it's usually the same version, but I'd load Production/@champion explicitly.

Serving, Docker, CI/CD
Walk me through what happens on git push.easy

Checkout, Python, pip cache, install; dvc repro (retrain + register to Staging); model tests; promote to Production; Flask tests; ECR login; docker build, tag, push; kubeconfig; create/update the Secret; kubectl apply.

After a push, are the pods running the new image?hard

Not necessarily: the tag is always :latest and the manifest doesn't change, so kubectl apply is a no-op and pods aren't restarted. Fix with git-SHA tags or kubectl rollout restart.

CI vs CD?easy

CI builds and tests every change automatically; CD releases changes that pass to production automatically.

What is training–serving skew? Do you have it?hard

Serving transforms inputs differently from training. Yes: the app cleans in a different order (URLs removed last), so URLs leave tokens like "http imdb com". Fix: one Pipeline artifact plus a parity test.

Flask's server vs Gunicorn?easy

Flask's is a single-process dev server. Gunicorn is a production WSGI server with a master and worker processes. Mine runs 1 sync worker by default; I'd add workers and switch Prometheus to multiprocess mode.

Why Docker? How would you improve your Dockerfile?medium

Same environment everywhere. Improvements: copy requirements first for layer caching, --no-cache-dir, a non-root user, explicit gunicorn/scikit-learn pins, and bake the model in.

How do you handle secrets?medium

GitHub Secrets in CI; a Kubernetes Secret injected via secretKeyRef in pods; nothing in code or images. Next steps: OIDC instead of access keys, KMS encryption for Kubernetes Secrets.

Hardest CI bug?easy

CI hanging because dagshub.init wanted a browser login. I read the logs, saw it waiting on OAuth, and switched to token auth from secrets. Automation must be non-interactive.

Kubernetes, AWS, monitoring
Why Kubernetes instead of one server?medium

Keeps 2 replicas running, restarts crashed pods, spreads traffic, scales easily. Honestly one server would do for this traffic; I used EKS to learn production orchestration and deleted it after to control cost.

Pod vs Deployment vs Service?easy

A pod runs the container; a Deployment keeps N pods running and rolls out updates; a Service gives them one stable address (here an AWS load balancer).

Requests vs limits?medium

Requests are reserved for scheduling (256Mi, 250m CPU); limits are caps (512Mi, 1 CPU). Over the memory limit the container is OOM-killed; over CPU it's throttled.

Readiness vs liveness probe?medium

Readiness: may this pod receive traffic (important while the model downloads). Liveness: is it stuck, restart it. I'd add both.

How would you autoscale?medium

A Horizontal Pod Autoscaler on CPU or on request rate from Prometheus, with min/max replicas.

What do you monitor, and why a histogram?easy

Request count, latency (histogram, for p95/p99 rather than a misleading average), and predictions per class.

Write a PromQL query for p95 latency.hard

histogram_quantile(0.95, sum by (le) (rate(app_request_latency_seconds_bucket[5m]))).

How would you detect drift?hard

Track the prediction mix, input length and vocabulary coverage; compare live vs training distributions with PSI or KS; alert in Grafana; label samples to measure real accuracy and retrain through the pipeline.

Data drift vs concept drift?medium

Data drift: inputs change. Concept drift: the input→label relationship changes. Both degrade the model over time.

Canary vs blue-green vs shadow?hard

Canary: a small share of traffic to the new model, then expand. Blue-green: two full environments, switch all at once, instant rollback. Shadow: the new model scores live traffic silently for comparison.

Behavioural
What did you learn?easy

The model is the smaller part; reproducibility, testing, secrets, deployment and monitoring take most of the effort. Debug CI one step at a time and read logs carefully.

What would you do differently?medium

One shared preprocessing artifact from day one, negation-aware features, all params in params.yaml, real test thresholds and a promotion gate, path filters, SHA image tags, and failing loudly in every stage.

How did you decide which model to deploy?easy

Evidence: baseline, controlled 10-run comparison, cross-validated tuning, all tracked in MLflow. Best F1, also weighing speed and simplicity.

How did you manage cloud cost?easy

Deleted the cluster, node group and ECR images right after validating: EKS bills hourly even when idle.
